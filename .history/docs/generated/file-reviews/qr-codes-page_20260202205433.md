## 2. Execution Flow

### Initial Load Sequence
1. Component mounts → Extract `profile.shop_id` from auth context
2. Main `useEffect` triggers `loadQrCodes()` when dependencies change:
   - `profile.shop_id`, `currentPage`, `itemsPerPage`, `searchTerm`, `filterStatus`, `sortBy`, `sortOrder`
3. Server-side paginated query:
   - Apply status filter (`unused`, `assigned`, `sold`, `lost`, or `all`)
   - Apply search filter (case-insensitive ILIKE on `code` field)
   - Sort by selected column (`code`, `status`, `created_at`)
   - Range query: `.range(from, to)` for current page
4. Separate stats query via `getStats()` → Count each status type independently
5. Selection state cleared via separate `useEffect` on filter/page change
6. UI renders with stats cards, generation form, table, and pagination

### Bulk Generation Flow
1. User fills form: `prefix` (e.g., "WA-"), `startNumber` (e.g., 1), `quantity` (e.g., 100)
2. Preview shows range: "WA-00001 to WA-00100"
3. Submit → `handleGenerate()` creates array of code objects
4. Batch insert with `.insert(codes).select()`
5. **Error Handling**:
   - Duplicate key error (23505) → Custom message showing range attempted
   - Other errors → Generic message
6. Success: Reset to page 1, auto-increment `startNumber` for next batch

### Deletion Flows

**Single Delete**:
1. Click delete icon → Check if `status === 'unused'` (else blocked)
2. `setConfirmDialog` → Show custom ConfirmDialog
3. User confirms → Delete by ID → Reset to page 1

**Bulk Delete**:
1. User selects checkboxes (only unused codes shown with checkboxes)
2. Click "Delete (X)" button → Show confirmation
3. User confirms → `.delete().in('id', Array.from(selectedIds))`
4. Clear selection → Reset to page 1

**Delete All Unused**:
1. Click "Delete All Unused" (only visible when filter is `unused`)
2. Query count first for confirmation message
3. Show confirmation: "Delete ALL X unused QR codes?"
4. User confirms → `.delete().eq('status', 'unused')`
5. Reset to page 1

### Pagination Flow
- User changes page → `setCurrentPage(value)` → `useEffect` triggers reload
- User changes items per page → Reset to page 1 + reload
- Keyboard navigation: Arrow Left/Right for prev/next page (guards against input focus)
- Pagination displays: "Showing X to Y of Z"

### Sorting Flow
- User clicks column header → `toggleSort(column)`
- If same column → Toggle between `asc` and `desc`
- If different column → Set new column with `asc` order
- `useEffect` dependency triggers reload with new sort

### Export Flow
1. Click "Export" → Fetch ALL matching records (no pagination)
2. Convert to CSV format: "Code,Status,Created At"
3. Create Blob → Download as file: `qr-codes-YYYY-MM-DD.csv`

### View Details Flow (Assigned/Sold Codes)
1. Click eye icon on non-unused code → `setViewingQrCode(qr)`
2. Opens `QrCodeDetailsDialog` with full QR code data
3. Dialog shows inventory item details, sale info (if sold)

## 3. Business Rules & Assumptions

### Critical Business Logic

**QR Code Generation Rules**:
- Prefix: Any string (typically shop-specific, e.g., "WA-", "SHOP1-")
- Number: Zero-padded to 5 digits (e.g., 1 → "00001")
- Uniqueness: Enforced by database constraint (duplicate insert fails)
- Initial status: Always `unused` on creation
- Batch limit: Max 1000 per generation (HTML max attribute)

**Status Lifecycle**:
- **unused**: Generated but not assigned to inventory
- **assigned**: Linked to inventory item (available for sale)
- **sold**: Item sold at POS (terminal state)
- **lost**: Manually marked as lost/damaged (admin action)

**Deletion Rules**:
- **Only `unused` codes can be deleted** (data integrity)
- Deleting `assigned`/`sold` codes would break inventory links
- Bulk delete automatically filters to unused only
- "Delete All Unused" button only visible when filter is `unused`

**Pagination Strategy**:
- Server-side pagination (fetches only current page records)
- Default: 50 items per page
- Options: 10, 25, 50, 100, 200, 500
- Total count tracked separately (`.count: 'exact'`)

**Search Behavior**:
- Case-insensitive substring search (`.ilike('code', '%search%')`)
- Searches only the `code` field (not status or dates)
- Server-side search (not client-side filtering)
- Cleared when page/filter changes

### Implicit Assumptions

1. **Shop Isolation**: RLS policies ensure `shop_id` filtering (not explicitly checked in code)
2. **QR Code Uniqueness**: Database constraint prevents duplicates (app doesn't pre-check)
3. **Status Transitions**: Code assumes status changes happen elsewhere (POS, inventory assignment)
4. **Prefix Conventions**: No validation on prefix format (accepts any string, including empty)
5. **Number Sequence**: App suggests next number but allows manual override
6. **Selection Persistence**: Selections cleared on page change (not persisted across pages)

### Edge Cases Not Handled

- **Empty Prefix**: Can generate codes like "00001", "00002" (no prefix separator)
- **Overlapping Ranges**: Can re-generate same codes if user doesn't increment start number
- **Large Batch Timeout**: 1000 code generation may timeout database insert
- **Export Memory**: Exporting 100k+ codes may crash browser (no pagination in export)
- **Duplicate Detection**: Duplicate error message shows attempted range but not which specific codes exist

## 4. Risks & Edge Cases

### High Priority Risks

**No Pre-Generation Duplicate Check**:
- **Risk**: Users must manually track used number ranges to avoid duplicates
- **Impact**: Generation fails with unclear error message after attempting insert
- **User Confusion**: "Some codes already exist" but doesn't show which ones
- **Recommended Fix**: Query max existing number for prefix, suggest next available range

**Large Batch Generation Performance**:
- **Risk**: Inserting 1000 codes at once may timeout or lock database
- **Impact**: Generation fails, user loses progress
- **Current Mitigation**: Max 1000 quantity limit (HTML attribute)
- **Recommended Fix**: Batch insertions in chunks of 100, show progress bar

**Export Memory Limitation**:
- **Risk**: Exporting 50k+ QR codes loads entire dataset into browser memory
- **Impact**: Browser tab crashes or freezes
- **Current State**: No warning or pagination for export
- **Recommended Fix**: Warn users before exporting >10k records, add export pagination

**Stats Performance (5 Separate Queries)**:
- **Risk**: Every page load triggers 5 separate count queries
- **Impact**: Increased database load, slower page renders
- **Current State**: `getStats()` runs 5 queries (`total`, `unused`, `assigned`, `sold`, `lost`)
- **Recommended Fix**: Single query with `GROUP BY status` or cached aggregation

### Medium Priority Risks

**Selection State Loss on Filter/Page Change**:
- **Risk**: User selects 20 codes, changes filter → Selection cleared
- **Impact**: Must re-select codes if accidentally changes view
- **Current State**: `useEffect` clears selections intentionally (by design)
- **Recommended Fix**: Consider persisting selections across pages (track by ID set globally)

**No Optimistic Updates**:
- **Risk**: Delete/Generate → Fetches fresh data after action
- **Impact**: Slight delay showing updated UI
- **Recommended Fix**: Optimistic update (update state immediately, revert on error)

**Prefix Auto-Increment Logic**:
- **Risk**: After generating 100 codes, `startNumber` increments by 100
- **Impact**: If user generates again without changing, creates sequential codes
- **Edge Case**: If generation fails midway (partial insert), startNumber still increments
- **Recommended Fix**: Only increment on successful insert

### Low Priority Edge Cases

| Edge Case | Description | Impact |
|-----------|-------------|--------|
| Zero/Negative Start | Form allows negative numbers | Invalid codes like "WA--0001" |
| Empty Prefix | No warning for prefix-less codes | Codes like "00001" generated |
| Lost Status | No UI to mark codes as "lost" | Status only set via database |
| Sorting on Status | String sort, not logical order | "assigned" before "sold" alphabetically |
| Select All | Only selects unused codes on CURRENT page | Doesn't select all unused globally |
| Keyboard Nav | Arrow keys guarded against input focus | ✅ Correctly handled |

## 6. Refactor Signals

### Immediate Refactoring Needs (High Priority)

**Optimize Stats Queries**:
- **Current**: 5 separate count queries per page load
- **Proposed**: Single aggregation query with GROUP BY:
  ```sql
  SELECT status, COUNT(*) as count
  FROM qr_codes
  WHERE shop_id = $1
  GROUP BY status;
  ```
- **Benefits**: 5x faster, single round-trip to database

**Extract Pagination Logic**:
- **Current**: Pagination calculations inline (startItem, endItem, totalPages)
- **Proposed**: Custom hook:
  ```typescript
  const { currentPage, setCurrentPage, startItem, endItem, totalPages, PaginationControls } = 
    usePagination({ totalCount, itemsPerPage });
  ```
- **Benefits**: Reusable across pages, less boilerplate

**Pre-Check Duplicate Codes**:
- **Current**: Insert fails with unclear error if duplicates exist
- **Proposed**: Query max existing number for prefix before generation:
  ```typescript
  const { data: maxCode } = await supabase
    .from('qr_codes')
    .select('code')
    .eq('shop_id', shop_id)
    .ilike('code', `${prefix}%`)
    .order('code', { ascending: false })
    .limit(1);
  // Extract number, suggest next available
  ```
- **Benefits**: Better UX, prevents errors

**Separate Component: `QrCodeGenerationForm`**:
- **Lines**: 583-632 (generation card)
- **Reason**: Self-contained form with validation
- **Interface**: `<QrCodeGenerationForm onGenerate={handleGenerate} shopId={profile.shop_id} />`

### Medium Priority Refactoring

**Batch Insert Chunking**:
- **Current**: Inserts all codes at once (max 1000)
- **Proposed**: Chunk into batches of 100 with progress:
  ```typescript
  for (let i = 0; i < codes.length; i += 100) {
    const chunk = codes.slice(i, i + 100);
    await supabase.from('qr_codes').insert(chunk);
    setProgress((i + chunk.length) / codes.length * 100);
  }
  ```
- **Benefits**: Prevents timeouts, shows progress

**Extract Table Component**:
- **Lines**: 669-813 (table rendering)
- **Reason**: Complex table with sorting, selection, actions (145 lines)
- **Interface**: `<QrCodeTable codes={qrCodes} onDelete={handleDelete} onView={handleViewDetails} />`

**Memoize Filtered Codes**:
- **Current**: Checkbox enable calculation done inline multiple times
- **Proposed**: `const unusedCodesOnPage = useMemo(() => qrCodes.filter(...), [qrCodes]);`

**Export Memory Warning**:
- **Current**: Exports unlimited records
- **Proposed**: Check count, show warning if >10k records
