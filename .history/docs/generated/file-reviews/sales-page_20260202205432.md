## 1. File Responsibility

**Primary Purpose**: Display server-side paginated sales transactions with comprehensive filtering (date, search, sale type), sorting, statistics, bill preview with PDF/print, and CSV export.

**Role in the System:**  
Central sales reporting interface. Shows all completed sales with customer info, payment method, discounts, and sale type breakdown. Links to detailed reports (festival, clearance).

**What This File Intentionally Does NOT Do:**  
- Does NOT create sales (handled by POS)
- Does NOT edit or delete sales (audit trail integrity)
- Does NOT process returns (separate workflow needed)
- Does NOT send bills (BillPreviewDialog handles display only)

**Key Dependencies:**
- `@/lib/api/sales` - `fetchSales()` (partially used)
- `@/context/AuthContext` - Shop ID for multi-tenancy
- `@/hooks` - `useDateFilter`, `useServerPagination`, `useSortableTable`, `useDebouncedSearch`
- `@/components/shared/DateFilterTabs` - Date range selection
- `@/components/shared/SortableHeader` - Sortable column headers
- `@/components/shared/BillPreviewDialog` - Bill preview with print/PDF/email

## 2. Execution Flow

### Initial Load Sequence
**Trigger:** Component mount with authenticated user  
**Dependencies:** `profile.shop_id`, `dateFilter`, `currentPage`, `itemsPerPage`, `debouncedSearchTerm`, `sortBy`, `sortOrder`, `saleTypeFilter`  
**Internal Steps:**  
1. `useDateFilter` hook calculates `startDateISO` based on filter (today/week/month/all)
2. `loadSales()` builds Supabase query with all filters
3. Fetches paginated results + separate stats query for full dataset

---

### loadSales() - Main Data Fetch (Lines 55-145)
**Trigger:** Any filter/pagination change  
**Internal Steps:**  
1. Build query with `sale_items` join
2. Apply date filter: `.gte('created_at', startDateISO)`
3. Apply search: `.or('customer_name.ilike.%...%,customer_phone.ilike.%...%')`
4. Apply sort and pagination: `.order(sortBy).range(from, to)`
5. **Client-side sale type filtering** after fetch (Lines 90-107)
6. Separate stats query for FULL dataset (Lines 109-145)

**Critical Design Decision:**  
Sale type filtering happens client-side because `sold_on_sale` and `sale_type` are on `sale_items`, not `sales`. Would require complex subquery or RPC for server-side.

**Stats Calculation (Fixed Jan 2026):**  
Stats now query full filtered dataset, not just current page. Includes:
- Total sales count, revenue, discount, average
- Festival/Clearance/Promotion breakdowns

---

### Sale Type Filtering Logic (Lines 90-107)
**Types:**
- `regular` - ALL items NOT on sale
- `mixed` - Has BOTH sale and regular items
- `festival/clearance/promotion` - Has at least one item of that type

**WHY Client-Side:**  
Cannot efficiently filter parent `sales` by child `sale_items` fields in Supabase without RPC.

### BillPreviewDialog Integration (Line 44, 660)
**New Feature (Jan 2026):**  
Clicking eye icon opens `BillPreviewDialog` with:
- Full invoice layout with Womaniya branding
- Multiple print formats (A4, 80mm thermal, 58mm thermal)
- PDF generation via jsPDF + html2canvas
- Web Share API for mobile sharing

---

### exportSales() - CSV Export (Lines 195-252)
**Trigger:** User clicks "Export" button  
**Internal Steps:**  
1. Fetches ALL matching sales (ignores pagination)
2. Includes sale type breakdown per sale
3. Columns: Bill Number, Customer, Phone, Items (Regular/Festival/Clearance/Promotion), Payment, Amount, Date, Time

## 3. Business Rules & Assumptions

**Explicit Rules:**
- Stats calculated from FULL filtered dataset (not page)
- Sale type badges: 🟢 festival, 🔴 clearance, 🔵 promotion
- Date filters: Today (midnight), Week (7 days), Month (calendar), All Time
- Search on customer name/phone only (NOT bill number)
- Default sort: `created_at` descending

**Implicit Assumptions:**
- `bill_prefix` exists on all sales (fallback: empty string)
- `sale_items` always joined (may be empty array)
- Walk-in customer when `customer_name` is null

**Business Logic:**
- Festival sales link to `/admin/reports/festival`
- Clearance sales link to `/admin/reports/clearance`
- Promotion sales have no dedicated report yet

## 6. Refactor Signals

### Immediate Refactoring Needs (High Priority)

**Add Bill Number to Search**:
- **Current**: Search only works on customer name/phone
- **Proposed**: Include bill_number in ILIKE query
- **Example**: `.or(\`customer_name.ilike.%${search}%,customer_phone.ilike.%${search}%,bill_number.ilike.%${search}%\`)`
- **Benefits**: Users can find bills by number

**Add Search Debouncing**:
- **Current**: Every keystroke triggers server query
- **Proposed**: Use `useDebouncedValue` hook (300ms delay)
- **Benefits**: Reduced API calls, better performance

**Implement View Details**:
- **Current**: Eye button has no onClick handler
- **Proposed**: Link to `/admin/sales/[id]` or open detail dialog
- **Benefits**: Complete feature, consistent with other pages

**Fix Stats to Show Total Dataset**:
- **Current**: Stats calculated from current page only
- **Proposed Options**:
  1. Add separate stats query for total revenue/discount
  2. Show "Page Stats" vs "Total Stats" clearly
  3. Use the `count` from pagination for total bills
- **Benefits**: Accurate financial overview

### Medium Priority Refactoring

**Extract Custom Hook: `useSalesData`**:
- **Current**: Data fetching logic mixed with component
- **Proposed**:
  ```typescript
  const { sales, loading, error, totalCount, stats, refetch } = useSalesData({
    shop_id: profile?.shop_id,
    dateFilter,
    searchTerm,
    sortBy,
    sortOrder,
    page: currentPage,
    pageSize: itemsPerPage,
  });
  ```
- **Benefits**: Testable, reusable, cleaner component

**Replace Alert with Toast**:
- **Current**: Export uses `alert()` for feedback
- **Proposed**: Use `toast.success()` like rest of app
- **Example**: `toast.success(\`Exported ${data.length} sales\`)`

**Add Error State UI**:
- **Current**: Errors logged to console only
- **Proposed**: Add error state with retry:
  ```typescript
  if (error) return <ErrorState message={error.message} onRetry={loadSales} />;
  ```

**Extract Pagination Component**:
- **Current**: Pagination controls inline (~80 lines)
- **Proposed**: Create reusable `<PaginationControls>` component
- **Benefits**: Reusable across pages (QR codes, inventory, finances)

### Low Priority Refactoring

**Memoize Stats**:
- Use `useMemo` to avoid recalculating on every render

**Add Export Warning for Large Datasets**:
- Check count before export, warn if >10k records

**Separate SaleRow Component**:
- Extract table row rendering for cleaner code

**Loading State Improvement**:
- Add shimmer effect to skeleton loading
