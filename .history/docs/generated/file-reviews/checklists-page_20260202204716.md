## 1. File Responsibility

### Primary Responsibility
Admin interface for managing checklist templates, including CRUD operations on templates and items, with completion history tracking.

### Role in the System
- Creates and edits checklist templates with recurrence rules
- Manages checklist items (add, remove, reorder)
- Creates daily instances for active checklists
- Displays completion history and statistics

### What This File Intentionally Does NOT Do
- **Complete checklist items**: Done in staff-facing UI, not admin panel
- **Assign to specific staff**: Checklists are shop-wide, not per-staff
- **Schedule future instances**: Only creates "today's" instances
- **Archive vs delete**: Templates are hard-deleted

### Key Dependencies
| Dependency | Purpose |
|------------|---------|
| `@/context/AuthContext` | Current user profile (shop_id, user_id) |
| `@/lib/supabase` | Direct DB access for orphan cleanup |
| `@/lib/api/checklists-v2` | API functions for all checklist operations |

## 2. Execution Flow

### `ChecklistsManagementPage` Component

**Trigger:** Route navigation to `/admin/checklists`

**Input Expectations:**
- User must be authenticated with valid `profile.shop_id`

**Internal Steps:**
1. On mount, fetch all checklist templates with items
2. Display in filterable card grid
3. Handle CRUD operations via dialogs

**Side Effects:**
- **DB Read**: Checklist templates and items via API
- **DB Write**: Template/item CRUD operations
- **State**: Filter, dialog, and form states

**Output/UI:**
- Stats cards (Total, Active, Inactive, Total Items)
- Search and filter tabs
- Card grid of checklist templates
- Create/Edit dialog with item management
- History dialog with stats

### `loadChecklists()`

**Trigger:** `useEffect` on `profile.shop_id` change

**Steps:**
1. Call `getChecklistTemplates(shop_id)` API
2. Returns templates with nested items
3. Cast to local `ChecklistWithItems` type

### `handleSaveChecklist()`

**Trigger:** Save button in create/edit dialog

**Validation:**
1. Name must not be empty
2. At least one item required
3. Recurrence days required (unless 'once' type)

**For New Checklist:**
1. Call `createChecklistTemplate()` with all form data and items

**For Existing Checklist:**
1. Call `updateChecklistTemplate()` with form data
2. Delete ALL existing items
3. Re-create items from current list

**Key Behavior:** Items are fully replaced, not individually updated. This simplifies reordering but loses item history.

### `handleCreateTodaysInstances()`

**Trigger:** "Create Today" button click

**Steps:**
1. Get today's date and day of week
2. Query existing instances for today
3. **Orphan cleanup**: Delete instances where template recurrence no longer matches today
4. Call `createChecklistInstances()` to generate new instances

**Key Business Logic:** Cleans up orphaned instances when admin changes recurrence days mid-day.

### `handleViewHistory(checklist)`

**Trigger:** "History" button on checklist card

**Steps:**
1. Open history dialog immediately
2. Fetch last 30 days of completion history (parallel Promise.all)
3. Fetch stats (completion rate, counts)
4. Display in dialog

### Item Management in Dialog

| Action | Handler | Behavior |
|--------|---------|----------|
| Add item | `handleAddItem()` | Validates non-empty, generates temp ID |
| Remove item | `handleRemoveItem(id)` | Filters from local state |
| Reorder | `handleMoveItem(index, direction)` | Swaps positions, updates sort_order |
| Toggle day | `handleToggleDay(day)` | Toggles day in recurrence_days array |

## 3. Business Rules & Assumptions

### Explicit Business Rules

| Rule | Implementation |
|------|----------------|
| Recurrence types: daily, weekly, once | Select dropdown, affects day selector visibility |
| Weekly checklists need active days | Array of 0-6 (Sun-Sat), validated non-empty |
| Default recurrence days: Mon-Sat | Initial state `[1,2,3,4,5,6]` |
| Checklist must have ≥1 item | Validation before save |
| Items have sort_order | Maintained on reorder, used for display |
| Orphan cleanup on instance creation | Removes instances for non-matching days |

### Implicit Assumptions
- Checklists are shop-specific
- Day 0 = Sunday (JavaScript convention)
- Template creator is tracked via `created_by`
- Items are displayed in sort_order sequence
- History limited to 30 days for performance

### Invariants
- Template ID is immutable
- Item sort_order is 0-indexed continuous sequence
- Active checklists create instances, inactive don't

## 4. Risks & Edge Cases

### High Priority

| Risk | Impact | Mitigation |
|------|--------|------------|
| Item deletion on edit | Loses completion history links | Items recreated with new IDs |
| Hard delete templates | No recovery | Uses `confirm()` dialog |
| Orphan cleanup race | Could delete valid instances | Runs before create, but no transaction |

### Medium Priority

| Risk | Impact | Mitigation |
|------|--------|------------|
| Large item counts | Dialog overflow | `overflow-y-auto` on dialog content |
| Concurrent template edits | Last write wins | No optimistic locking |
| No undo for item removal | Accidental loss | Only in local state until save |

### Low Priority

| Risk | Impact | Mitigation |
|------|--------|------------|
| Empty template name | Blocked | Validation check |
| Duplicate template names | Allowed | No unique constraint check |
| Very old history | Memory on stats | Limited to 30 days |

## 6. Refactor Signals

### Structural Issues
1. **Largest file at 840 lines**: Strong candidate for extraction:
   - `useChecklistForm` hook for form state
   - `ChecklistCard` component
   - `ChecklistFormDialog` component
   - `ChecklistHistoryDialog` component
2. **Unused import**: `Link` from 'next/link' imported but not used
3. **Type assertion**: `data as any as ChecklistWithItems[]` suggests type mismatch with API

### Scalability Concerns
1. **No pagination**: All templates loaded at once. Unlikely to be many per shop, but grid could be virtualized.
2. **Sequential item operations**: Save deletes then creates items one-by-one. Could batch with transactions.
3. **History fetches all completions**: For very active checklists, 30 days × items × staff = large payload

### Pattern Misalignments
1. **Mixed data access**: Uses API functions AND direct supabase calls for orphan cleanup
2. **No React Query**: Manual loading states, no caching of templates
3. **window.history.back()**: Could use router for consistent navigation pattern

### Suggested Improvements (No Code)
- Extract dialog components to reduce file size
- Add batch item update API to avoid delete-recreate cycle
- Use `router.back()` instead of `window.history.back()`
- Add loading skeleton for grid while fetching
- Consider drag-and-drop for item reordering
- Transaction wrapper for orphan cleanup + instance creation

### What Feels Dated or Unpolished ❌

| Issue | Impact | Premium Comparison |
|-------|--------|-------------------|
| **841 lines in one file** | Hard to maintain | Should be split into components |
| **Manual up/down reorder** | Click 10 times to move item 10 spots | Todoist uses drag-drop |
