## 1. File Responsibility

**Primary Responsibility:**  
Server-side paginated inventory listing with filtering, sorting, category stats, export, and deletion capabilities.

**Role in the System:**  
Central inventory management interface for admin users. Displays all inventory items with QR codes, categories, sizes, prices, and status. Provides real-time stats dashboard and category breakdown cards.

**What This File Intentionally Does NOT Do:**  
- Does NOT create or edit inventory items (delegated to `/add-lot/page.tsx`)
- Does NOT handle POS-specific operations (selling, QR scanning)
- Does NOT modify lot details (price, category, size)
- Does NOT perform batch operations beyond single-item deletion

**Key Dependencies:**
- `@/context/AuthContext` - Requires `profile.shop_id` for all queries
- `@/lib/supabase` - Direct database access
- `@/hooks` - `useServerPagination`, `useSortableTable`, `useDebouncedSearch`
- `@/components/shared/SortableHeader` - Reusable sortable column headers
- `@/components/shared/StatsCardGrid` - Clickable stats cards
- `@/components/shared/InventoryItemDetailsDialog` - Item detail modal
- `@/components/shared/ConfirmDialog` - Delete confirmation

## 2. Execution Flow

### Component Mount & Data Loading
**Trigger:** Component renders with authenticated user  
**Input:** `profile.shop_id` from AuthContext  
**Internal Steps:**  
1. `useEffect` triggers on `profile.shop_id` availability
2. Parallel calls: `fetchInventory()`, `fetchCategories()`, `fetchCategoryStats()`
3. Separate `useEffect` for `getStats()` when inventory changes

**Side Effects:**  
- Multiple database queries initiated
- Loading skeletons displayed during fetch

---

### fetchInventory() - Main Data Query (Lines 158-227)
**Trigger:** Mount, pagination, filter, sort, or search changes  
**Input:** Current state: `currentPage`, `itemsPerPage`, `debouncedSearchTerm`, `statusFilter`, `categoryFilter`, `sortBy`, `sortOrder`  
**Internal Steps:**  
1. Builds Supabase query with nested joins (`qr_codes`, `lots`, `categories`, `sizes`)
2. Applies filters: status, category ID, search term
3. Maps `sortBy` to actual column names (Lines 200-213)
4. Uses `useServerPagination` hook for `from`/`to` range calculation
5. Executes with `.range(from, to)` and `{ count: 'exact' }`

**Side Effects:**  
- Database query with complex joins
- Updates `inventory[]` and `totalCount`

**Output:** Paginated inventory items with full relational data

---

### fetchCategoryStats() - Separate Full Dataset Query (Lines 229-275)
**Trigger:** Component mount only  
**Input:** `profile.shop_id`  
**Internal Steps:**  
1. Fetches ALL inventory items (NOT paginated) with category info
2. Aggregates in-memory using `Map`: total, available, sold per category
3. Sorts by total (descending), takes top 6

**WHY Separate Query:**  
Cannot derive accurate category totals from paginated results. Accepts one heavy query on mount for accurate stats.

---

### getStats() - Global Count Queries (Lines 60-85)
**Trigger:** `useEffect` when `inventory` changes  
**Internal Steps:**  
1. Four separate count queries using `{ count: 'exact', head: true }`
2. No actual data fetched, just counts

**Performance Note:** Runs 4 queries on every inventory change. Consider caching.

---

### handleDeleteItem() - Deletion with QR Cleanup (Lines 109-140)
**Trigger:** User clicks delete icon on available item  
**Internal Steps:**  
1. Opens `ConfirmDialog` with item QR code
2. On confirm: Delete QR code first, then inventory item
3. Refresh inventory list

**WHY Delete QR First:**  
Foreign key constraint. Deleting item first would leave orphaned QR.

**RISK:** No transaction - if QR deletes but item fails, QR is lost.

## 3. Business Rules & Assumptions

### Authorization Rules
1. **Admin-Only Access:** Route is under `(protected)/admin/` - assumed middleware enforces admin role
2. **Shop Isolation:** All queries filtered by `profile.shop_id` - no cross-shop data access
3. **Profile Required:** Component waits for `profile?.shop_id` before querying (Line 51)

### Data Shape Assumptions
1. **QR Code Relationship:** Assumes every inventory item has exactly one QR code via `qr_code_id` foreign key
2. **Lot Relationship:** Assumes every inventory item belongs to one lot with pricing/category
3. **Category Optional:** Handles null category gracefully with "No category" fallback (Line 677)
4. **Size Optional:** Displays either `sizes.size_name` or `free_text_size` or "No size" (Line 680)

### Deletion Constraints
1. **Available Only:** Delete button only shown for items with `status='available'` (Line 713)
2. **No Deletion After Sale:** Sold/damaged items cannot be deleted - preserves sales history
3. **QR Code Reuse:** Deleted item's QR code becomes available for future lots

### Pagination Invariants
1. **Page Bounds:** Current page cannot exceed `totalPages` or go below 1
2. **Items Per Page:** Supported values: 10, 25, 50, 100, 200, 500 (Lines 785-790)
3. **Auto-Reset:** Changing `itemsPerPage` resets to page 1 (Line 777)

### Search Behavior
1. **Debounce Missing:** Search triggers on every keystroke - no debouncing implemented
2. **Case-Insensitive:** Uses `.ilike` for search (Line 159)
3. **Multi-Column:** Searches across QR code and category name (OR condition)

### Export Business Rules
1. **Respects Filters:** Export includes only currently filtered items
2. **No Pagination:** Exports ALL filtered items regardless of page
3. **Column Selection:** Exports: QR Code, Category, Size, Status, Price, Date (Line 357)

## 4. Risks & Edge Cases

### Runtime Failure Risks

**High Risk: Stats Query Performance (Lines 198-244)**  
- Fetches ALL inventory items for category stats calculation
- For shops with 50,000+ items, this query could timeout or consume excessive memory
- No caching, runs on every mount
- **Mitigation:** Add database view or materialized view for category aggregates

**High Risk: Export Memory Exhaustion (Lines 329-376)**  
- Exports entire filtered dataset to memory before download
- 10,000+ items with full relational data could freeze browser
- No chunking, no streaming, no progress indicator
- **Mitigation:** Add export size limit (e.g., max 5000 items) with warning

**Medium Risk: Multiple Count Queries (Lines 60-85)**  
- Four separate database queries for simple counts
- Runs after every inventory change (Line 327 dependency)
- Could cause rate limiting on high-traffic shops
- **Mitigation:** Combine into single query using PostgreSQL aggregation

**Medium Risk: Deletion Without Transaction (Lines 109-139)**  
- Two sequential deletes: QR code then inventory item
- If QR delete succeeds but item delete fails, QR code is orphaned and lost
- No rollback mechanism
- **Mitigation:** Use Supabase RPC/function with database transaction

**Low Risk: Search Without Debounce (Line 538)**  
- Query fires on every keystroke
- Could create database load with fast typers
- **Mitigation:** Add 300ms debounce on search input

### Silent Failure Scenarios

**Missing Error Handling on Export (Line 372)**  
- Generic alert for export errors, no specific error message
- Network failures show "Failed to export inventory" with no retry
- Large exports fail silently if browser runs out of memory

**Category Filter Breaking on Deleted Category**  
- If category in `categoryFilter` gets deleted by another admin, filter query silently returns no results
- No "Category not found" message, appears as if inventory is empty
- Should clear filter or show warning

**Stale Stats After Bulk Operations**  
- If another admin deletes 100 items, stats cards show outdated numbers until refresh
- No real-time updates, no periodic polling
- User sees incorrect totals

### Missing Validations

1. **No Confirmation on Page Navigation Away:** User could lose filter/search state accidentally
2. **No Check for Active Sales:** Deleting available item doesn't verify it's not in an active cart
3. **No Duplicate Detection:** If QR code foreign key constraint is removed, duplicate QR codes could exist
4. **No Shop Ownership Verification:** Relies entirely on auth middleware for shop isolation

### Security/Authorization Risks

**Low Risk: RLS Policy Dependency**  
- All queries rely on Supabase RLS policies for shop isolation
- If RLS policies are misconfigured, admins could see other shops' inventory
- No additional client-side validation of shop_id ownership

**Low Risk: Deletion Race Condition**  
- No optimistic locking on deletion
- If two admins try to delete same item simultaneously, both could succeed (unlikely but possible)

**Low Risk: XSS in QR Code Display (Line 672)**  
- QR codes displayed as-is without sanitization
- If QR code contains malicious script (unlikely but possible if manually inserted), could execute
- **Mitigation:** QR codes should be validated at creation to be alphanumeric only

## 6. Refactor Signals

### Performance & Scalability

**Stats Queries Duplication (Lines 60-244)**  
- Three separate functions doing similar counting: `getStats()`, `fetchCategoryStats()`, and implicit count in `fetchInventory()`
- Consider consolidating into single database view or materialized view that pre-calculates all stats
- Could reduce 6+ queries on mount to 1-2 queries

**Export Architecture (Lines 329-376)**  
- Client-side CSV generation doesn't scale beyond 10,000 items
- Consider:
  - Edge function/server action for CSV generation
  - Streaming response for large exports
  - Background job with email delivery for very large exports

**Search Without Debouncing (Line 538)**  
- Creates database query on every keystroke
- Move to `useDebouncedValue` hook or `debounce` utility (300ms delay)

### Data Fetching Patterns

**Mixed Client-Side State Management**  
- Using multiple `useState` hooks for filters (Lines 24-35)
- Pagination state mixed with filter state
- Consider `useReducer` for complex filter state management

**No Query Key Management**  
- Manual dependency management in `useEffect` (Line 54)
- Consider React Query or SWR for:
  - Automatic cache management
  - Optimistic updates on deletion
  - Background refetching
  - Stale-while-revalidate patterns

**Cascading Queries**  
- `fetchInventory()` triggers `getStats()` which triggers re-render
- Three separate queries on mount with no coordination
- Consider `Promise.all()` to parallelize and show loading state once

### Deletion Logic

**Two-Step Deletion Process (Lines 118-129)**  
- Sequential deletes without transaction
- If second delete fails, QR code is orphaned
- **Refactor:** Create Supabase Edge Function:
  ```sql
  CREATE OR REPLACE FUNCTION delete_inventory_item_with_qr(item_id UUID)
  RETURNS void AS $$
  BEGIN
    DELETE FROM qr_codes WHERE id = (SELECT qr_code_id FROM inventory_items WHERE id = item_id);
    DELETE FROM inventory_items WHERE id = item_id;
  END;
  $$ LANGUAGE plpgsql;
  ```

### UI/UX Patterns

**Alert Usage Instead of Toast (Lines 370, 373, 376)**  
- Using native `alert()` for export feedback
- Inconsistent with rest of app using Sonner toasts
- Replace with `toast.success()` and `toast.error()`

**Hardcoded Pagination Options (Lines 785-790)**  
- Items per page values hardcoded in JSX
- Consider moving to constants file: `PAGINATION_OPTIONS = [10, 25, 50, 100, 200, 500]`

**Stats Cards as Filters (Lines 432-451)**  
- Clever UX pattern but not immediately discoverable
- Consider visual indication (hover effect shows "Click to filter")
- Add tooltip or label

### Type Safety

**`any` Types Throughout (Lines 22, 26, 29, 30, 109)**  
- `inventory`, `categories`, `categoryStats`, `viewingItem` all typed as `any[]` or `any`
- Import proper types from `@/types`:
  ```tsx
  import type { InventoryItem, Category, Lot } from '@/types';
  const [inventory, setInventory] = useState<InventoryItem[]>([]);
  ```

**Nested Data Access Without Type Guards (Line 677)**  
- `item.lots?.categories?.name` - multiple optional chains without validation
- Type system cannot verify this path exists at runtime

- Component handles loading inline with skeleton (Lines 589-598)
- No Next.js 13+ `loading.tsx` or `error.tsx` files
- Consider route-level boundaries for better UX

**Search Params Not Used**
